# 0.2.2 代码与用色复核：八项问题尚未闭环

2026-09-17。复核提交 `78fc1ca`，运行构建 `f5fbbea9eeb65bb3`。本次为分析与文档更正，不修改运行代码，不发布新的效果版本。

## 结论与交付表述更正

**0.2.2 是局部构图、深度系数和绘制顺序调整，未完成《0.2.1 视觉复诊》提出的整体视觉重构。八项问题没有任何一项可以按整项认定已达到设计目标。** 铁路高度/缩放解耦、薄云与日月的绘制顺序等子项有明确完成；不能把这些子项推广为“空间层次和光照已解决”。

此前报告虽然列出了剩余差距，但以“技术检查通过”组织交付，缺少八项逐条验收，也没有完成原文要求的灰度/色彩范围核对。66 项测试验证了实现约束和运行行为，不能作为画面达到概念稿的证据。这个验收方法需要纠正。

### 关于“33 行修改”

`git show --numstat 78fc1ca`：整个提交 13 个文件，新增 267 行、删除 81 行；五个场景实现文件新增 162 行、删除 75 行，另有 45 行测试与文档/版本调整。不能确认用户界面中“33 行”的统计口径。

但更大的 diff 数字不改变复核结论：不少改动是图层参数、系数、格式及绘制拆分。问题是缺少对应的造型、用色和构图机制及实景验收，不是必须写够某个行数。少量 shader 代码也可以带来很大变化，前提是它确实解决了目标问题。

## 用色证据：实际提取，而非印象判断

### 材料及方法

- 原始视频本地时间 4 秒与 15 秒各取一帧。二者显示不同人工参数；不把它们当作自然昼夜或自动变化的证明。
- 已确认概念稿 `docs/concepts/revision-02/A-warm-cloud-valley.png`。
- 0.2.2 已保存的真实固定样板 `sunset.png`：seed=8472，distance=0，phase=0.74，fog=0.28，clouds=0.64，shape=0.6。裁掉工具栏和车体放大检查区，保留完整场景。
- 另取 seed=12345、distance=9000、phase=0.74 的实景，检查结论是否只来自一个种子。
- 全景按宽 600 像素做相同 BOX 采样，视作 sRGB 转 D65 CIELAB；固定随机种子 22，K-means k=12、n_init=5，最多 24,000 个训练像素，全部有效采样像素统计面积。视频标题、设置面板、作者文字及推荐标记不进入统计。
- 色块按 L* 明度排序；色块百分比表示该聚类的有效画面占比。局部云图各提取 8 色，仅用于观察；矩形中含少量天空/山，不是严格的云分割，结论数字来自全景。
- 不统计原始唯一 RGB 个数：渐变、抗锯齿、视频压缩都会制造很多近似颜色。固定提取 12 色也不表示一张图只有 12 种颜色。

### 全景结果

| 样本 | 平均色度 C* | C*>35 的面积 | 明度 L* 的 5%–95% |
| --- | ---: | ---: | ---: |
| 视频 4 秒 | 37.3 | 59.7% | 36.0–85.5 |
| 视频 15 秒（另一组参数） | 32.1 | 39.3% | 26.1–83.7 |
| 概念 A | 27.6 | 21.7% | 24.9–84.4 |
| 0.2.2 / seed 8472 | 20.6 | 0.2% | 39.2–77.4 |
| 0.2.2 / seed 12345 | 20.8 | 0.3% | 40.0–78.6 |

L* 取值约 0–100；C* 为离中性灰轴的距离，不是 HSV 饱和度。C*>35 是本次用于展示颜色强度分布的固定阈值，不是美术达标线。这些是选定图像的描述性统计，受构图、截图/录屏和不同材质覆盖影响；不能据此推算全时段效果或给作品打分。

**稳定观察：** 两个实际样本都缺少具有面积的鲜明色区，并且明暗范围收窄。概念 A 并没有视频那么鲜艳，但仍通过冷暖分工与更宽的明暗范围形成丰富感。因此不应直接把视频的高色度面积当作软件目标。

### 代表色与画面中的职责

- 视频 4 秒能分出深赭红 `#8D423B`、红橙 `#E1432F`、橘色 `#EC7849`、杏色 `#F69568`、暖白及蓝天。几种相邻暖色拥有各自清楚的块面，而非都平均混在一起。
- 概念 A 有深蓝灰 `#363A52`、蓝紫 `#65618B`、紫玫瑰 `#AA7D95`、珊瑚 `#F38670`、杏橙 `#FAB28E` 和浅杏金 `#FCCDA3`。深色承托、冷色云腹、中间转折和亮面同时存在。
- 实际主色是灰紫 `#665770`、灰玫瑰 `#9B7474`、灰桃 `#B38379`、浅桃 `#E1A089` 与米杏 `#E9B89A`。冷蓝主要停留在天空，主云里的冷暖跨度明显弱；大量相近中间色占据画面。

这些 HEX 是图像聚类代表色，不是原作者的源代码色板。

## 代码为什么压缩了用色

### P1：昼夜色板未改，空间用色仍主要靠三色插值

`lighting.ts:4–98` 的 keys 在 0.2.1 → 0.2.2 中没有变化。phase=0.74 时，云影/云身/云亮仍为 `#886888 / #F09E87 / #FFDFAB`，再叠加天空/地平线色及深度修正。九个时间节点并不等于同一时刻有九组丰富色层。

`nature.ts:229` 仍是 shadow→body→light 两次混合。插值能产生无数 RGB 数值，但没有独立控制冷云腹、珊瑚转折、杏金朝光面、薄云透光与蓝紫环境色各自的空间面积。只增加 HEX 或噪声也不能解决这种缺失。

### P1：深度处理压暗了颜色，却没充分建立色相职责

`nature.ts:305–316` 先把 body 向 shadow 混合，再乘较小系数；近景 light 又向已压暗的 body 混合。原诊断要求避免仅靠整层压暗，实际实现仍较多依赖这种方法。它增强某些近远亮度差，却可能同时丢失局部明亮暖面。

`lighting.ts` 中 cloudNearShade/cloudNearBody/cloudFarShade 仍被计算，但当前自然云路径已不读取它们；原先近云阴影少量 violet 偏色也没有沿这条新路径继承。这不是运行错误，却说明颜色角色并未系统整合。

### P1：局部光照只重配现有颜色，不能生成足够的冷暖关系

sourceBand 调整 illumination / lit / rim 权重。太阳一侧因此可能更亮，但仍在同一组颜色范围内变化，没有独立的暖侧光、冷环境光、厚云阴影职责。它也没有与 valley 开口协调。

### P2：混色步骤与统一雾色会进一步趋同

云主体、阴影、高光连续混合，之后再与同一个 horizon 色按雾系数混合。就当前色板与面积而言，这使灰粉/灰桃中间色占得更多，不能只从源色板中存在珊瑚和杏金就判断画面已经用上它们。

### P1：验收测了输入系数，没有验收最终图像结构

`tests/depth.test.ts:15–40` 检查最远/最近层的 body/shadow uniform 亮度比及光源坐标传入。它不运行 fragment shader、不包含可见面积、遮挡、最终混色和全部中景，也无法发现主云仍只有相近桃色。测试本身有用，但不能命名/解读为实际画面层次已通过。

## 后续应按什么顺序重做

1. **先建立一个固定暖霞视觉样板**：锁定种子、旅程、取景和时段，让最终画面同时出现深蓝紫承托、偏紫云腹、珊瑚转折、杏金受光与克制亮边。分别给出近/中/远的亮暗范围和大致面积；用图像检查，不以 uniform 数值通过代替。
2. **重写云团的色面分配**：大体积/中尺度转折/少量边缘分别负责什么，哪些位置保持安静。颜色沿形体与受光组织，不随机撒彩色噪声，不用全局饱和度拉满代替。
3. **建立跨层的观看通道**：远山、远云、中景和近景共同响应开放/封闭区段，开口与主要受光方向协调；让缩略图能看出连续递远的景观。
4. **重做山形与面内关系**：轮廓、肩部、沟谷和色面共用形体依据；桥脚消隐、窗光、薄云笔触随之协调。
5. **再迁移到白天/月夜与连续昼夜**：同世界彩色/灰度对照、多个种子、正常速度、低画质运动检查。美术样板未达标前，不以新增功能或打包测试代替。

本轮不承诺必须改多少行，也不将上述内容包装为又一次小修即可解决。需要保留已正确的运动/平台基础，对着色和构图的核心规则进行实质性迭代。
